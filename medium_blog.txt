A hands-on guide to IVF and HNSW internals — how they work, what they cost, and how to tune recall, latency, memory, and updates for real workloads.

You’ve got millions (or billions) of embeddings and a product team that wants “instant” search. Exact k-NN is a non-starter. The question isn’t whether to use an approximate nearest neighbor (ANN) index — it’s which one and how to tune it. Let’s be real: most outages here are self-inflicted by the wrong defaults.

Below is the practical, inside-the-engine view of IVF (Inverted File) and HNSW (Hierarchical Navigable Small World), plus the tradeoffs that actually move your p95.

The problem both are solving
We need fast top-k over high-dimensional vectors under a distance metric (cosine/L2/IP). ANN indexes shrink the search space with structures that cheaply skip most vectors while retaining good recall (how often the true neighbors show up).

Key levers you’ll tune no matter the index:

Recall ↔ latency: scan more = higher recall = higher latency.
Build time & memory: what it takes to construct and store the index.
Mutation cost: how inserts/deletes/updates behave at steady state.
Skew tolerance: how uneven data or query distributions hurt you.
IVF internals (Inverted File)
Mental model: cluster the space into nlist coarse centroids; each centroid holds an inverted list of assigned vectors. At query time, compute distances to centroids, pick the top nprobe lists, then scan just those lists (often with compressed vectors), re-ranking exact distances on a small candidate set.

Core knobs

nlist — number of coarse clusters. Bigger = shorter lists = faster scans, but more RAM and longer training.
nprobe — lists to visit per query. Bigger = higher recall & latency.
Compression — Product Quantization (PQ/OPQ) or residual PQ to store codes in RAM (or GPU) with tight memory. You can re-rank on original vectors or on residuals for accuracy.
Strengths

Predictable latency when data is static or slowly changing.
Excellent memory efficiency with PQ (10–30× smaller than raw float32).
Easy to scale horizontally by sharding lists.
Weak spots

Training drift: centroids trained on old distributions degrade recall.
Skew: hot lists get long; your tail becomes “that one shard.”
Deletes/updates: cheap to append, trickier to compact; tombstones accumulate.
Typical tuning ranges

nlist: ~√N to 4√N (e.g., N=10M → 3k–12k). Start mid, measure.
nprobe: 1–2% of nlist for interactive search; go higher for recall-heavy analytics.
PQ code size: 8–16 bytes per vector for 768-D; add re-rank on originals if you need fidelity.
HNSW internals (Hierarchical Graph)
Mental model: multi-layer proximity graph. Upper layers have few nodes/edges; bottom layer is dense. Search starts high, greedily walks toward the query, and drops levels, retaining a candidate beam of promising nodes.

Core knobs

M — max edges per node (graph connectivity). Bigger = better recall & memory.
efConstruction — beam width at build time; higher gives higher-quality edges & longer builds.
efSearch — beam width at query time; higher = more recall & latency.
Strengths

Great recall at low latency for interactive workloads.
Robust to skew; the graph routes around dense regions.
Online inserts are straightforward (local link updates).
Weak spots

Memory heavy: edges cost. Expect ~ (M * 8–16 bytes) overhead per node + vector storage.
Build time can be significant with large efConstruction.
Deletes are awkward (lazy mark + rebuild periodically).
Typical tuning ranges

M: 12–48 (start at 16 or 32).
efConstruction: 100–400 (start at 200).
efSearch: 50–200 (start at 64–128; push up for recall).
IVF vs HNSW: where each wins
Choose IVF when

Data is large and mostly static (catalogs, image banks).
Memory is tight; PQ/OPQ is acceptable with re-rank.
You want strict latency SLOs with steady distributions.
You plan to shard by list and re-train on a schedule
Choose HNSW when

You need high recall with low latency on dynamic corpora.
Mixed or skewed queries; tails matter more than median.
You can afford extra RAM for graph edges.
You favor smooth online inserts over periodic training.
The hybrid reality

IVF-HNSW (HNSW as a coarse quantizer) or HNSW + PQ exist in some engines: use a fast graph to shortlist, then PQ re-rank.
Multi-stage retrieval: filter by metadata → ANN shortlist → exact re-rank on originals.
Cost dimensions that actually bite
Memory footprint
IVF with PQ: 1–2 bytes per dimension is common; great for GPUs and big RAM saves.
HNSW: vector storage + edges; a 768-D float32 vector (~3 KB) plus M=32 edges can easily push >4 KB per vector before compression.
Build time
IVF: dominated by k-means training and list assignment. Scales well on GPUs.
HNSW: dominated by efConstruction. Parallelizable, but heavier.
Mutations
IVF: inserts append to lists; deletes are tombstones until you compact or rebuild lists. Re-train periodically to prevent drift.
HNSW: inserts immediate; deletes best handled with lazy marks + occasional rebuilds.
Latency vs recall
IVF: tune nprobe. Doubling often yields diminishing returns beyond a point.
HNSW: tune efSearch. Returns usually degrade gracefully; tails rise if efSearch too small.
Tuning playbook (cut-and-try, but disciplined)
Fix the metric & normalizations. Cosine vs L2 changes everything; normalize once at ingestion if using cosine on dot-product engines.
Start small, measure real queries. Synthetic random queries lie. Use your production query mix.
Pick a memory target first. That decides IVF+PQ vs raw/HNSW. Then chase recall.
Drive by SLOs, not vibes.
Define recall@k target (e.g., 0.95 at k=10).
Define p95 latency (e.g., 80 ms API-level).
Tune until both hold under peak concurrency.
5. Watch the tail. Hot lists (IVF) or hubs (HNSW) create p99 cliffs. If p99 explodes while p95 looks fine, you’ve got skew.

Minimal code to make it concrete
IVF-PQ (Faiss-style Python)
import faiss
import numpy as np

d = 768                     # vector dim
nb = 10_000_000             # database size
nlist = 8192                # coarse clusters
m = 16                      # PQ codebooks (d must be divisible by m)
k = 10                      # top-k

# train on a sample
train = np.random.randn(200_000, d).astype('float32')
quantizer = faiss.IndexFlatL2(d)
index = faiss.IndexIVFPQ(quantizer, d, nlist, m, 8)  # 8 bits/codebook
index.train(train)

# add base vectors (normally in batches)
xb = np.random.randn(nb, d).astype('float32')
index.add(xb)

# tune recall/latency via nprobe
index.nprobe = 64
xq = np.random.randn(1000, d).astype('float32')
D, I = index.search(xq, k)
Notes: If recall is low, raise nprobe or use OPQ/residual PQ and re-rank top candidates with original vectors.

HNSW (Faiss-style Python)
import faiss, numpy as np
d = 768; nb = 10_000_000; k = 10

index = faiss.IndexHNSWFlat(d, 32)  # M = 32
index.hnsw.efConstruction = 200

# add data
xb = np.random.randn(nb, d).astype('float32')
index.add(xb)

# tune recall/latency via efSearch
index.hnsw.efSearch = 128
xq = np.random.randn(1000, d).astype('float32')
D, I = index.search(xq, k)
Notes: Increase efSearch for recall, but watch p99; concurrency amplifies queueing in CPU-bound graphs.

Pitfalls (and the fixes that actually work)
Centroid drift (IVF): if the data distribution shifts quarterly, your recall quietly dies. Fix: scheduled re-training with a fresh sample and partial rebuilds.
Long tail lists (IVF): a few lists hoard vectors. Fix: split hot lists (increase nlist), adopt residual quantizers, or shard by a stable key.
Over-connected hubs (HNSW): M too small or poor construction yields few hubs that absorb traffic. Fix: raise M and efConstruction; rebuild.
Deletes/updates: both structures prefer periodic compaction. Budget a background job; don’t let tombstones exceed a few percent.
Measuring recall wrong: top-k with ties or metric mismatches distort results. Fix: compute exact k-NN on a held-out slice (hundreds of thousands of points), and report recall@k with the same metric & normalization as prod.
Quick decision matrix
| Constraint                        | Favor IVF                     | Favor HNSW                 |
| --------------------------------- | ----------------------------- | -------------------------- |
| Memory tight                      | ✅ (with PQ/OPQ)               | ❌ (edge-heavy)             |
| High update rate                  | ⚠️ (works, compaction needed) | ✅ (inserts are cheap)      |
| Highest recall at low latency     | ⚠️ (raise nprobe + re-rank)   | ✅ (raise efSearch)         |
| Predictable p95 under static data | ✅                             | ✅                          |
| Billion-scale + GPU build         | ✅ (train/assign on GPU)       | ⚠️ (heavier, but possible) |
| Skewed query distribution         | ⚠️ (watch hot lists)          | ✅ (graph routes around)    |
Closing
There’s no silver bullet — you’re trading memory, build time, and mutation friction for recall and latency. IVF gives you disciplined, memory-efficient lanes with occasional retraining. HNSW gives you nimble, high-recall search that loves inserts but eats RAM. Start from your SLOs, pick the index that satisfies your constraints, and then move the two levers that matter for each: nprobe for IVF, efSearch (plus M) for HNSW. Your users won’t notice the index you chose—they’ll notice the milliseconds you saved.
